# Front-end e engine para jogo idle: pet de desktop (Windows/Linux/macOS) → screensaver Android

Pesquisa feita em 24/11/2026. Priorizei documentação oficial; fontes não oficiais estão identificadas como tais. "Incerteza" significa que não encontrei fonte primária suficiente nesta rodada.

## 1. Quais opções de engine/front-end e como comparam (peso, curva, performance, animação 2D, janelas pequenas/transparentes)?

### Takeaway
Para um jogo 2D leve de vocabulário, a combinação com melhor relação peso/controle é **TS + Canvas/CSS (ou PixiJS/Phaser) dentro de um wrapper nativo fino (Tauri no desktop; Capacitor + plugin nativo no Android)**. Godot é uma alternativa sólida se você quiser uma engine completa com transparência por pixel e exportação multiplataforma; Unity, Flutter e .NET MAUI são viáveis, mas resolvem menos do problema específico do "pet na taskbar" e do Daydream do que aparentam.

### Cited Findings
- **Phaser** é framework HTML5 2D (WebGL e Canvas), usa JavaScript/TypeScript e seu foco declarado é o navegador; conversão para apps nativos é feita por ferramentas de terceiros — [Phaser Docs](https://docs.phaser.io/). `Phaser.AUTO` tenta WebGL e cai para Canvas; o Animation Manager é global (3.60+); o FX pipeline (glow, blur etc.) é **somente WebGL**; Arcade Physics é descrito como simples e leve para navegadores móveis — [Phaser - First Game](https://docs.phaser.io/phaser/getting-started/making-your-first-phaser-game); [Phaser FX](https://phaser.io/oss/docs/phaser/concepts/fx); [Phaser Display](https://docs.phaser.io/phaser/concepts/display).
- **PixiJS v8** é um motor de renderização 2D (WebGL/WebGL2, com WebGPU e Canvas2D como opções) com scene graph, Assets, Ticker e eventos de ponteiro; a doc cita explicitamente integração com Tauri e Electron — [PixiJS Intro](https://pixijs.com/8.x/guides/getting-started/intro); [PixiJS Architecture](https://pixijs.com/8.x/guides/concepts/architecture). O renderer WebGPU é experimental e a doc recomenda WebGL para produção; o Canvas2D tem recurso reduzido — [PixiJS Rendering](https://pixijs.com/8.x/guides/components/renderers); [PixiJS Application](https://pixijs.com/8.x/guides/components/application). O v8 passou a ter tree shaking melhor e carrega apenas o backend usado — [PixiJS v8 launch](https://pixijs.com/blog/pixi-v8-launches).
- **Godot 4** expõe configurações de janela `per_pixel_transparency/allowed`, `size/always_on_top`, `size/borderless`, `size/transparent` — [Godot ProjectSettings](https://docs.godotengine.org/en/stable/classes/class_projectsettings.html). A doc de `DisplayServer` diz que transparência por pixel existe em Windows, macOS, Linux (X11/Wayland) e Android, mas a disponibilidade varia com driver de GPU, display manager e compositor; no Android só é habilitada via ProjectSettings — [Godot DisplayServer](https://docs.godotengine.org/en/stable/classes/class_displayserver.html). Exportação Web exige WebAssembly + WebGL 2; C# no Godot 4 não exporta para Web; export single-thread desde 4.3 é o padrão e evita SharedArrayBuffer/cross-origin isolation; a própria doc diz que export Web em mobile é bem mais lento que o nativo — [Godot Web export](https://docs.godotengine.org/en/latest/tutorials/export/exporting_for_web.html).
- **Unity** recomenda explicitamente stripping de código, compressão Brotli, desligar development build, baixar nível de gráficos e comprimir texturas para reduzir tamanho de builds Web/mobile — [Unity distribution size](https://docs.unity3d.com/6000.2/Documentation/Manual/webgl-distributionsize-codestripping.html); [Unity WebGL optimization](https://docs.unity3d.com/2022.3/Documentation/Manual/web-optimization-player.html); [Unity mobile WebGL](https://docs.unity3d.com/2022.3/Documentation/Manual/web-optimization-mobile.html). Isso confirma que o tamanho exige trabalho ativo; a doc não fornece um número único de "peso base".
- **Tauri 2** usa a webview do sistema (WebView2 no Windows, WKWebView no macOS, webkitgtk no Linux) e um core Rust; app mínimo pode ter **menos de 600 KB** porque não embute motor de navegador — [Tauri start](https://v2.tauri.app/start/); [Tauri process model](https://v2.tauri.app/concept/process-model/). Suporta janelas `transparent`, `alwaysOnTop`, `alwaysOnBottom`, efeitos Mica/Acrylic (que exigem janela transparente) e `noRedirectionBitmap` para evitar flash branco no Windows — [Tauri Window API](https://v2.tauri.app/reference/javascript/api/namespacewindow/). No macOS, transparência exigia `macOSPrivateApi` e o schema avisava que isso **impede aceitação na App Store**; a doc de configuração diz que isso virou um no-op em Tauri 2.12.1+ — [Tauri schema](https://schema.tauri.app/config/2); [Tauri config](https://v2.tauri.app/reference/config/).
- **Electron** expõe `BrowserWindow` com opção `transparent`, `setAlwaysOnTop(flag, level, relativeLevel)` (níveis mais altos aparecem acima da taskbar/Dock; Apple desaconselha acima de `screen-saver`), `setSkipTaskbar`, `backgroundThrottling` e `ready-to-show` — [Electron BrowserWindow](https://www.electronjs.org/docs/latest/api/browser-window). A mesma doc alerta que no Wayland não é possível posicionar/redimensionar janelas programaticamente de forma geral e que `setAlwaysOnTop` não é suportado no Wayland.
- **Flutter** tem uma base de código compartilhada com embedders próprios por plataforma (Android, iOS, macOS, Windows, Linux); no Windows o runner é um app Win32 C++ cuja criação/tamanho da janela pode ser editada em `main.cpp` — [Flutter architecture](https://docs.flutter.dev/resources/architectural-overview); [Flutter desktop](https://docs.flutter.dev/platform-integration/desktop); [Flutter Windows](https://docs.flutter.dev/platform-integration/windows/building). No Android, `FlutterFragment` suporta transparência, mas a doc diz explicitamente que isso **prejudica performance** e, com `SurfaceView`, a surface transparente fica acima de todas as outras views; platform views não estão disponíveis no desktop — [FlutterFragment](https://docs.flutter.dev/add-to-app/android/add-flutter-fragment); [Flutter architecture](https://docs.flutter.dev/resources/architectural-overview).
- **.NET MAUI** usa um projeto único multi-target para Android, iOS, macOS e Windows (WinUI 3 no Windows) com pasta `Platforms/` para código nativo — [MAUI overview](https://learn.microsoft.com/en-us/dotnet/maui/what-is-maui?view=net-maui-10.0); [MAUI single project](https://learn.microsoft.com/en-us/dotnet/maui/fundamentals/single-project?view=net-maui-10.0).
- **Capacitor** é runtime nativo para web apps (iOS, Android e PWA); no Android exige API 24+ e WebView Chrome 60+, com projeto Android gerado e aberto no Android Studio; plugins customizados acessam SDKs nativos — [Capacitor](https://capacitorjs.com/); [Capacitor Android](https://capacitorjs.com/docs/android).

### Inferences
- Para animação 2D, PixiJS dá o controle mais fino com menos "baggage" de engine; Phaser dá mais produtividade (cenas, animações, input, física) com custo de bundle maior. Para vocabulário idle, um `setInterval`/requestAnimationFrame + Canvas puro pode ser suficiente — isso é inferência a partir das docs, não um benchmark.
- A restrição real não é a engine e sim a **integração com o sistema operacional** (janela topological, transparência, ciclo de vida). Isso favorece Tauri/Flutter/MAUI sobre uma engine de jogo pura.
- Unity e Godot são "engine first"; se o jogo é basicamente texto, cartões e sprites simples, o peso de ferramental não se justifica sem necessidade de editor/asset pipeline.

### Gaps
- Não encontrei números oficiais e comparáveis de bundle/tamanho de runtime para Phaser, PixiJS, Godot, Flutter e MAUI; só o "<600 KB" do Tauri e as recomendações de otimização da Unity.
- Não verifiquei suporte documentado de janela pequena/transparente em .NET MAUI Windows nem API pública Flutter desktop para sempre-acima/opacidade; trate como incerto até protótipo.
- Não encontrei benchmark oficial de bateria/consumo comparando essas opções em janela minúscula.

## 2. Como se implementa um "pet na barra de tarefas"? O que é viável sem hacks e o que quebra com updates?

### Takeaway
**Desenhar dentro da taskbar do Windows 11 não é uma API suportada.** O caminho robusto é: ícone na bandeja/menu bar para controle + janela própria transparente/sem borda posicionada sobre a barra (ou logo acima dela); alternativas oficiais são AppBar (reserva espaço) e Widgets (painel de widgets). No macOS o análogo estável é `NSStatusItem` na barra de menu; no Linux, X11 é mais previsível e Wayland exige layer-shell/extensão do shell.

### Cited Findings
- **AppBar (API oficial Win32)**: uma janela âncora numa borda, registrada com `SHAppBarMessage`/`ABM_NEW`, com `ABM_QUERYPOS` + `ABM_SETPOS`, notificações `ABN_POSCHANGED`, `ABN_STATECHANGE`; o sistema garante que a taskbar fica na borda mais externa e há no máximo um appbar auto-oculto por borda — [Microsoft: Application Desktop Toolbars](https://learn.microsoft.com/en-us/windows/win32/shell/application-desktop-toolbars); [SHAppBarMessage](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shappbarmessage).
- **Widgets do Windows**: aparecem no Widgets Board (painel aberto pelo ícone da taskbar/Win+W), não como pet na barra; provider pode ser app Win32 empacotado ou PWA, com Adaptive Cards; conteúdo HTML via web widget tem disponibilidade restrita ao EEA — [Microsoft: Windows Widgets](https://learn.microsoft.com/en-us/windows/apps/design/widgets/); [Widget providers](https://learn.microsoft.com/en-us/windows/apps/develop/widgets/widget-providers); [Web widget providers](https://learn.microsoft.com/en-us/windows/apps/develop/widgets/web-widget-providers).
- **Sobrepor a taskbar é fragile**: o README do projeto open source MiniBar afirma que deskbands (`IDeskBand`) exigiam DLL carregada pelo Explorer e que o Windows 11 removeu esse mecanismo — a taskbar é XAML e não hospeda extensões de terceiros; a solução deles é uma janela topmost sobre os pixels livres, registrando-se como appbar com `ABM_NEW` mas **sem** `ABM_SETPOS`, lendo alinhamento dos ícones e o retângulo de `TrayNotifyWnd`; não aparece sobre jogo fullscreen exclusivo — [minibar-now-playing-overlay README](https://github.com/AceisX/minibar-now-playing-overlay).
- **Atualizações quebram customizações**: em 2023 o update opcional KB5022913 do Windows 11 22H2 fez ExplorerPatcher/StartAllBack impedirem boot; Microsoft atribuiu isso a métodos não suportados usados por apps de customização — [PCPer](https://pcper.com/2023/03/microsofts-war-against-third-party-ui-customization-for-windows-11/).
- **Projetos open source de referência**: Shimeji-Desktop (fork Java, Windows Vista+/macOS/Linux X11, comportamento em XML, licença BSD-ish) — [DalekCraft2/Shimeji-Desktop](https://github.com/DalekCraft2/Shimeji-Desktop); Shijima-Qt (C++/Qt6, Windows/macOS/Linux, KDE Plasma 6 e GNOME 46 em X11/Wayland; no GNOME instala plugin do shell e exige re-login; no macOS pede Accessibility; projeto **arquivado**, autor diz que Qt foi a framework errada pelos hacks) — [pixelomer/Shijima-Qt](https://github.com/pixelomer/Shijima-Qt); shimeji2 (Rust, menu-bar app sem ícone no Dock, cada pet é janela transparente sem borda com click-through) — [AlanJager/shimeji2](https://github.com/AlanJager/shimeji2); ShimeLinux (Java+Rust, AppIndicator pode ser necessário, Many DEs testados) — [BujjuIsABee/shimelinux](https://github.com/BujjuIsABee/shimelinux).
- **Detalhe prático Windows**: `HWND_TOPMOST` não vence a taskbar do Windows 11; o mushroom-pet insere a janela logo acima de `Shell_TrayWnd` e reafirma em timer, apenas no modo opcional de sobreposição — [rblurrr/mushroom-pet](https://github.com/rblurrr/mushroom-pet). Uma issue do Ebiten mostra o workaround `WS_EX_TOOLWINDOW` para esconder a janela da taskbar, sem suporte nativo da engine — [Ebiten issue #1518](https://github.com/hajimehoshi/ebiten/issues/1518).
- **macOS**: `NSStatusItem` é a API oficial para elemento na barra de menu, com botão, custom view, `isVisible` e, em versões recentes, sessão de interface expandida para mostrar janela associada — [NSStatusItem](https://developer.apple.com/documentation/appkit/nsstatusitem); [WWDC26 Modernize AppKit](https://developer.apple.com/videos/play/wwdc2026/289/).
- **Linux/Wayland**: a doc do Electron diz que no Wayland não se pode posicionar/redimensionar/focar janelas programaticamente sem input do usuário e recomenda Xwayland (`--ozone-platform=x11`) quando necessário — [Electron BrowserWindow](https://www.electronjs.org/docs/latest/api/browser-window). A experiência do Shijima-Qt confirma dependência de plugin do shell para rastrear janelas — [Shijima-Qt](https://github.com/pixelomer/Shijima-Qt).

### Inferences
- A opção menos frágil é **tray/menu-bar + janela small transparente posicionada acima da barra**, com degradação graciosa: se não conseguir sobrepor, fica "na área de trabalho" ao lado da bandeja. Sobrepor pixel a pixel da taskbar deve ser tratado como feature opcional e experimentada por versão do Windows.
- macOS não tem equivalente oficial de "pet dentro da barra inferior"; o produto precisa adaptar a metáfora (menu bar + janela) em vez de portar o hack do Windows.
- Linux não deve ser uma promessa única: X11 e Wayland/GNOME/KDE têm comportamentos diferentes; o custo de suporte é maior que o de Windows/macOS.

### Gaps
- Não encontrei documentação oficial do Microsoft dizendo explicitamente "deskbands foram removidos no Windows 11"; a afirmação vem de README de projeto terceiro (bem detalhado) e do histórico de updates quebrando customizações.
- Não verifiquei APIs oficiais para desenhar dentro da taskbar do macOS ou do GNOME Shell sem extensão.
- Não encontrei ListView/API estável do Windows para enumerar ícones da taskbar (o README do MiniBar diz que não são janelas e não podem ser enumerados).

## 3. Android: o que é Daydream, como funciona, foi descontinuado e quais alternativas existem?

### Takeaway
`DreamService` continua na referência oficial e **não aparece marcado como deprecado** em 24/11/2026, mas o modelo é "screensaver ativado pelo usuário nas configurações, disparado ao carregar/dockar", e **não há API pública para iniciar o dream programaticamente**. A UI foi desestimulada em muitos fabricantes e o AOD não tem API de terceiros verificada; as alternativas documentadas são live wallpaper (`WallpaperService`) e widgets de lockscreen.

### Cited Findings
- `DreamService`: ciclo `onAttachedToWindow` → `onDreamingStarted` → `onDreamingStopped` → `onDetachedFromWindow`; declaração no manifest com `android:permission="android.permission.BIND_DREAM_SERVICE"` (obrigatório API 21+) e intent-filter `android.service.dreams.DreamService`; `setContentView()`, `setInteractive()`, `setFullscreen()`, `setScreenBright()`, `finish()`, `wakeUp()`; `meta-data` com `previewImage`, `settingsActivity`, `showClockAndComplications` (este último só em large-screen); gestos podem usar `Window.setSystemGestureExclusionRects` — [Android Developers: DreamService](https://developer.android.com/reference/android/service/dreams/DreamService).
- Introduzido no Android 4.2: dream começa quando o aparelho está carregando ou dockado; **usuário habilita em Settings e escolhe qual dream usar**; dreams não são Activities, não entram no backstack/Recents e **não podem ser iniciados diretamente pelo app**; podem desenhar com View hierarchy, Canvas, OpenGL, SurfaceTexture e aceitar interação — [Android Jelly Bean](https://developer.android.com/about/versions/jelly-bean); [Android Developers Blog 2012](https://android-developers.googleblog.com/2012/12/daydream-interactive-screen-savers.html).
- O app pode abrir as configurações com `Settings.ACTION_DREAM_SETTINGS` (`android.settings.DREAM_SETTINGS`), mas a doc avisa que pode não haver Activity correspondente — [Settings](https://developer.android.com/reference/android/provider/Settings). `PowerManager.isInteractive` observa que o dispositivo é considerado interativo enquanto "dreaming" — [PowerManager](https://developer.android.com/reference/android/os/PowerManager).
- **Bateria**: o blog oficial avisa que dream com consumo alto de CPU pode tornar o carregamento lento e que o sistema para o dream se o dispositivo deixar de carregar — [Android Developers Blog 2012](https://android-developers.googleblog.com/2012/12/daydream-interactive-screen-savers.html).
- **Incerteza sobre descontinuação**: não há aviso de deprecation na página oficial consultada; fontes não oficiais divergem: um mantenedor do Projectivy diz que "não existe API do Android para iniciar o screensaver", que mudanças internas recente restringiram isso a apps do sistema e que restam apenas root/adb+Shizuku — [Projectivy issue #305 (2025)](https://github.com/spocky/miproja1/issues/305); thread do MacroDroid relata que a action de iniciar Daydream deixou de funcionar em Android 13+ e foi removida do app — [MacroDroid forum](https://www.macrodroidforum.com/index.php?threads%2Fdaydream-on-action-not-working.6697%2F=). Um artigo de consumer support afirma "largamente deprecado desde Android 10" — [Dr.Fone](https://drfone.wondershare.com/android-manage/android-basic-daydreams.html) — mas é fonte de baixa autoridade e **contradiz** a ausência de deprecation na API; trate como sinal de desenfase de UI, não como fato de API.
- Pacotes de dream AOSP ainda aparecem em perfis de dispositivos Android 13–16 em banco de dados comunitário (dado descritivo, não normativo) — [BAYTON com.android.dreams.basic](https://sysapps.bayton.org/packages/com.android.dreams.basic).
- **Live wallpaper (alternativa documentada)**: `WallpaperService` + `Engine`, `onCreateEngine()`, `SurfaceHolder`, `onVisibilityChanged` ("muito importante que o wallpaper só use CPU enquanto visível"), `setTouchEventsEnabled` default desligado, flags de home/lock (`WallpaperManager.FLAG_SYSTEM`/`FLAG_LOCK`) — [WallpaperService](https://developer.android.com/reference/android/service/wallpaper/WallpaperService); [WallpaperService.Engine](https://developer.android.com/reference/android/service/wallpaper/WallpaperService.Engine). Não substitui um screensaver interativo: fica atrás dos apps.
- **Widgets na lockscreen**: blog oficial diz que chegaram ao AOSP para tablets e mobile na release após Android 16 (QPR1), já disponíveis em Pixel Tablet; **todos os widgets são compatíveis**, com opt-out via categoria `not_keyguard` em `xml-36`; OEM pode escolher o gatilho (ex.: carregamento/dock) — [Android Developers Blog 2025](https://android-developers.googleblog.com/2025/03/widgets-on-lock-screen-faq.html).
- **Overlay ("pet" sobre outros apps)**: `SYSTEM_ALERT_WINDOW` exige declaração no manifest **e** concessão explícita pelo usuário via `ACTION_MANAGE_OVERLAY_PERMISSION`; `Settings.canDrawOverlays()` verifica — [Android Settings.CanDrawOverlays](https://learn.microsoft.com/en-us/dotnet/api/android.provider.settings.candrawoverlays?view=net-android-35.0). A Play trata permissões especiais como restritas, exige justificativa ligada à funcionalidade promovida, instruções e **vídeo de demonstração** no Permissions Declaration Form, com revisão que pode levar semanas — [Play Console: sensitive permissions](https://support.google.com/googleplay/android-developer/answer/16558241?hl=en); [Play Console: declare permissions](https://support.google.com/googleplay/android-developer/answer/9214102?hl=en). Android 12+ bloqueia toques de overlays não confiáveis (com ressalva de opacidade ≥ 0.8 em SAW) — [Android tapjacking](https://developer.android.com/privacy-and-security/risks/tapjacking).

### Inferences
- Para "proteção de tela interativa", a implementação correta é um `DreamService` com UI/Canvas própria e **instrução clara para o usuário ativar em Configurações**; não tente iniciar o dream por intent oculto nem use SAW como substituto.
- Um live wallpaper é um ótimo plano B de baixa fricção (o usuário escolhe wallpaper sem mexer em screensaver), mas não roda quando o app está sendo usado nem "toma conta" da tela.
- Widget de lockscreen é o caminho mais novo e alinhado à plataforma para mostrar progresso do jogo com o aparelho bloqueado, porém depende da versão/OEM.

### Gaps
- **Não encontrei documentação oficial de uma API para AOD de terceiros em phones**; só vi referência a "ambient mode" do sistema em `PowerManager.isInteractive`. Não recomendo AOD como feature até confirmação.
- Não encontrei comunicado oficial Android dizendo "Daydream foi descontinuado"; o que há é ausência de deprecation na API + relatos de terceiros sobre inicialização bloqueada.
- Não verifiquei se Fabricantes específicos (Samsung/Xiaomi) removem a opção de screensaver em Android 14/15; teste em dispositivos reais.
- Não encontrei API pública documentada para detectar "dream em execução" a partir de um app comum.

## 4. PWA/web + wrapper nativo (Tauri/Capacitor) cobre desktop e Android com uma base só? Comparação com Flutter e híbrido web + Compose

### Takeaway
**Dá para compartilhar quase toda a lógica e o renderer**, mas não dá para compartilhar um único wrapper: Tauri cobre desktop (+mobile) e Capacitor cobre Android/iOS/PWA, cada um com seu projeto nativo. Flutter e MAUI oferecem uma base mais uniforme, porém exigem código nativo para as superfícies especiais; um híbrido "web no desktop + Compose no Android" troca reuso por controle nativo.

### Cited Findings
- **Tauri 2** declara suporte a desktop (macOS, Linux, Windows) e mobile (iOS, Android), frontend HTML/JS/CSS com backend Rust/Swift/Kotlin, usando webview nativa e binários pequenos — [Tauri 2.0 release](https://v2.tauri.app/blog/tauri-20/); [Tauri start](https://v2.tauri.app/start/). API de janela cobre transparência, always-on-top/bottom e efeitos; a camada de permissões exige explicitar `core:window:allow-set-always-on-top` etc. — [Tauri Window API](https://v2.tauri.app/reference/javascript/api/namespacewindow/). O process model mostra core Rust + webviews e suporte a interfaces do tipo tray — [Tauri process model](https://v2.tauri.app/concept/process-model/).
- **Capacitor** cobre iOS 15+, Android 7+ e browsers modernos; desktop oficialmente **não** — Electron é listado como *community platform* — [Capacitor FAQ](https://capacitorjs.com/docs/getting-started/faqs); [Capacitor](https://capacitorjs.com/). Plugins nativos customizados são o mecanismo previsto para acessar recursos de plataforma — [Capacitor Android](https://capacitorjs.com/docs/android).
- **Flutter** compartilha código entre Android, iOS, Web e desktop, mas cada plataforma tem embedder/runner próprio; o Windows usa Win32 C++ editável — [Flutter architecture](https://docs.flutter.dev/resources/architectural-overview); [Flutter Windows](https://docs.flutter.dev/platform-integration/windows/building). Transparência no Android tem custo de performance documentado e platform views não existem no desktop — [FlutterFragment](https://docs.flutter.dev/add-to-app/android/add-flutter-fragment); [Flutter architecture](https://docs.flutter.dev/resources/architectural-overview).
- **MAUI** é single-project multi-target com pastas `Platforms/` para código nativo e WinUI 3 no Windows — [MAUI single project](https://learn.microsoft.com/en-us/dotnet/maui/fundamentals/single-project?view=net-maui-10.0); [MAUI overview](https://learn.microsoft.com/en-us/dotnet/maui/what-is-maui?view=net-maui-10.0).
- **PixiJS** documenta que pode ser integrado a Tauri/Electron; **Phaser** diz que seu foco é web e que a conversão nativa é feita por ferramentas de terceiros — [PixiJS Intro](https://pixijs.com/8.x/guides/getting-started/intro); [Phaser Docs](https://docs.phaser.io/).

### Inferences
- Arquitetura recomendada: **núcleo do jogo em TS puro** (estado idle, SRS de vocabulário, progressão, persistência) + **adaptador de render** (Canvas/PixiJS) + **adaptadores de superfície** (Tauri tray/janela; Capacitor Activity/DreamService/WallpaperService). Assim o "código único" é a regra de negócio, não a janela.
- Tauri + Capacitor é mais leve para começar que Flutter/MAUI se a equipe já tem JS/TS (perfil do projeto) e evita reescrever o renderer. O custo é manter dois wrappers e escrever plugins nativos Android.
- Flutter/MAUI ganham se o objetivo for uma app "normal" consistente em todas as plataformas e se a equipe quiser uma única linguagem de UI; não resolvem por si sós o pet na taskbar nem o DreamService.

### Gaps
- **Não verifiquei nesta rodada a documentação oficial do Jetpack Compose para `DreamService`/`WallpaperService`**; por isso não recomendo Compose como caminho comprovado para o screensaver.
- Não encontrei documentação que garanta reutilização direta de plugins Tauri dentro do Capacitor (são ecossistemas distintos).
- Não há benchmark oficial de startup/RAM entre as combinações acima em janela minúscula.

## 5. Caminho por fases (MVP → taskbar → Android), decisões reversíveis e riscos

### Takeaway
Comece **web puro**, valide o loop idle, embrulhe no **Tauri** para desktop (tray + janela transparente), e só depois leve o mesmo núcleo ao **Android via Capacitor com plugin nativo para DreamService/WallpaperService**. Mantenha a superfície nativa atrás de uma interface para poder trocar "pet sobre a taskbar" por "widget/tray" ou "live wallpaper" sem reescrever o jogo.

### Cited Findings
- Fase 0 (MVP web): Phaser e PixiJS são frameworks web com WebGL/Canvas e TS — [Phaser Docs](https://docs.phaser.io/); [PixiJS Intro](https://pixijs.com/8.x/guides/getting-started/intro). Capacitor aceita qualquer web app com `package.json`, diretório de assets e `index.html` — [Capacitor getting started](https://capacitorjs.com/docs/getting-started).
- Fase 1 (desktop): Tauri permite declarar `transparent`, `alwaysOnTop`, `decorations: false`, efeitos e configurar permissões por capability; `noRedirectionBitmap` mitiga flash branco no Windows — [Tauri Window API](https://v2.tauri.app/reference/javascript/api/namespacewindow/); [Tauri config](https://v2.tauri.app/reference/config/). AppBar é a API Win32 oficial para reservar espaço e receber notificações de mudança da taskbar — [Microsoft AppBars](https://learn.microsoft.com/en-us/windows/win32/shell/application-desktop-toolbars).
- Fase 2 (Android): DreamService exige manifest com `BIND_DREAM_SERVICE` e o usuário precisa habilitar nos Settings (`ACTION_DREAM_SETTINGS`) — [DreamService](https://developer.android.com/reference/android/service/dreams/DreamService); [Settings](https://developer.android.com/reference/android/provider/Settings). Alternativa: `WallpaperService` com `onVisibilityChanged` para só gastar CPU quando visível — [WallpaperService.Engine](https://developer.android.com/reference/android/service/wallpaper/WallpaperService.Engine); ou widget de lockscreen (AOSP pós-Android 16 QPR1) — [Android Blog 2025](https://android-developers.googleblog.com/2025/03/widgets-on-lock-screen-faq.html).
- Risco de loja/permissão: overlay exige `SYSTEM_ALERT_WINDOW` e revisão reforçada na Play, com vídeo demonstrativo; permissões especiais devem ser justificadas pela funcionalidade principal — [Play policy](https://support.google.com/googleplay/android-developer/answer/16558241?hl=en); [Play declaration](https://support.google.com/googleplay/android-developer/answer/9214102?hl=en); [tapjacking](https://developer.android.com/privacy-and-security/risks/tapjacking).
- Risco macOS/App Store: transparência via API privada impediu aceitação na App Store (com mudança em Tauri ≥2.12.1 segundo a doc) — [Tauri schema](https://schema.tauri.app/config/2); [Tauri config](https://v2.tauri.app/reference/config/).
- Risco de compatibilidade: a taskbar do Windows 11 não aceita extensões de terceiros e updates já quebraram ferramentas de customização; transparência depende de driver/compositor; Wayland limita posicionamento/alway-on-top — [MiniBar README](https://github.com/AceisX/minibar-now-playing-overlay); [PCPer](https://pcper.com/2023/03/microsofts-war-against-third-party-ui-customization-for-windows-11/); [Godot DisplayServer](https://docs.godotengine.org/en/stable/classes/class_displayserver.html); [Electron BrowserWindow](https://www.electronjs.org/docs/latest/api/browser-window).
- Risco de bateria: dream que consome CPU pode atrasar carregamento e é parado pelo sistema; wallpaper deve usar CPU só quando visível; Electron recomenda pausar trabalho caro quando `visibilityState` é hidden — [Android Blog 2012](https://android-developers.googleblog.com/2012/12/daydream-interactive-screen-savers.html); [WallpaperService.Engine](https://developer.android.com/reference/android/service/wallpaper/WallpaperService.Engine); [Electron BrowserWindow](https://www.electronjs.org/docs/latest/api/browser-window).

### Inferences
- **Decisões reversíveis**: (a) manter regra de negócio em módulo TS sem dependência de DOM; (b) expor `SurfaceAdapter` com operações `show/atualizaTexto/recebeInput/hide`; (c) tratar "sobrepor taskbar" como feature flag desligada por default, com fallback tray+janela; (d) no Android, implementar primeiro Activity/PWA e depois plugin DreamService, sem misturar lógica do jogo no Service.
- **Ordem recomendada dos riscos**: validar cedo transparência + always-on-top no Windows 11 alvo e no macOS; só então investir em animação. No Android, validar cedo se o dispositivo alvo realmente oferece a opção de screensaver e se o usuário consegue selecionar o dream.
- **Publicação**: Play pode atrasar/Manter pending revisão se houver permissão sensível; evite `SYSTEM_ALERT_WINDOW` no MVP Android e use DreamService/WallpaperService/widget.
